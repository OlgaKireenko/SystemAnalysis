# Итоговый проект

# 1. Контекст и границы задачи

## 1.1. Проблема

Клиенту необходимо получить микрозайм дистанционно, без посещения офиса организации.

Существующий процесс оформления займа должен позволять клиенту пройти необходимые проверки, передать заявку на рассмотрение и получить решение по заявке в цифровом виде.

Основная проблема, которую необходимо решить, — обеспечить понятный и управляемый процесс оформления микрозайма, в котором необходимые данные клиента последовательно проверяются, заявка передаётся во внешние системы, а результат проверки и решение по заявке корректно обрабатываются системой.

## 1.2. Цель разработки

Цель — реализовать функциональность онлайн-оформления микрозайма, которая позволит:

* выбрать предварительные условия займа;
* рассчитать предварительный график платежей;
* создать заявку на микрозайм;
* проверить необходимые данные клиента;
* получить информацию из БКИ;
* передать данные в СПР для принятия решения;
* обработать результат СПР;
* предоставить клиенту информацию о решении и условиях займа;
* при положительном решении перейти к оформлению займа.

## 1.3. Основные заинтересованные лица и участники

 - Клиент
 - Представитель бизнеса Банка (заказчик)
 - Технический эксперт Бюро кредитных историй (Внешняя система, предоставляющая кредитную историю клиента для оценки его долговой нагрузки)
 - Технический специалист СПР (Система принятия решения, которая анализирует данные заёмщика и кредитной заявки)
   
---

## 1.4. Scope

В рассматриваемую функциональность входит процесс оформления микрозайма от расчёта условий до создания заявки и немного затрагивает процесс скоринга.

### В scope входят:

1. Выбор предварительных условий займа.
2. Расчёт предварительного графика платежей
3. Получение согласия клиента на обработку персональных данных.
4. Создание заявки на микрозайм.
5. Проверка возраста и гражданства клиента.
6. Запрос кредитной истории клиента в БКИ.
7. Передача заявки в СПР и обработка ответа СПР (интеграция с СПР)
8. Формирование статуса заявки.
9. Предоставление клиенту информации о результате.
10. Обработка подтверждения/отказа клиента от предложенных условий займа.
11. Передача заявки на дальнейшее оформление сделки при положительном решении.

--

## 1.5. Out of scope

В рамках данной функциональности не рассматриваются:

* регистрация и авторизация пользователя в мобильном приложении;
* разработка самого БКИ;
* разработка/текстирование СПР;
* внутренние алгоритмы скоринга СПР;
* формирование кредитной истории клиента в БКИ;
* страхование займа от невыплаты;
* страхование жизни заёмщика;
* взыскание задолженности;
* сопровождение займа после его выдачи;

Внешние системы рассматриваются только с точки зрения интеграции с ними и обработки их ответов.

# 1.6. Существенные неопределённости

На данном этапе исходной постановки недостаточно для полного проектирования функциональности.

Основные неопределённости:

* какие именно данные необходимо предоставить клиенту для создания заявки;
* какие поля являются обязательными;
* какие проверки выполняются до создания заявки, а какие после;
* какие именно данные передаются в БКИ;
* какие данные передаются в СПР;
* какие статусы может иметь заявка;
* какие причины отказа необходимо возвращать клиенту;
* сколько заявок может быть у одного клиента;
* как обрабатываются технические ошибки внешних систем;
* что происходит с заявкой при недоступности СПР;
* какие изменения заявки разрешены после её создания;
* на каком этапе клиент может отказаться от кредита;

# 1.9. Допущения

На текущем этапе принимаются следующие допущения:

1. Клиент уже зарегистрирован и авторизован в мобильном приложении.
2. БКИ и СПР доступны через API.
3. Кредитный конвейер является системой, управляющей процессом обработки заявки (оркестратор) 
4. Решение по заявке принимает СПР на основании переданных данных и результатов необходимых проверок.
5. Кредитная история запрашивается у БКИ до принятия окончательного решения.
6. При временной недоступности СПР система выполняет повторные попытки обращения.
7. Клиент получает информацию о результате рассмотрения заявки через мобильное приложение.
8. При положительном решении клиент должен подтвердить предложенные условия перед дальнейшим оформлением сделки.
9. Внешние системы самостоятельно отвечают за свою внутреннюю бизнес-логику; кредитный конвейер отвечает за корректное взаимодействие с ними и обработку результатов.

# 2. Функциональные и нефункциональные требования, Бизнес - правила

## 2.1 Бизнес-правила

| ID | Бизнес-правило |
|:---|:---|
| BR-01 | **Обязательность данных клиента.** Заявка на получение микрозайма ВСЕГДА ДОЛЖНА СОДЕРЖАТЬ сведения о клиенте, который её подал. |
| BR-02 | **Проверка возраста и гражданства.** ТОЛЬКО ЕСЛИ клиент соответствует установленным требованиям по возрасту и гражданству, ТОГДА его заявка может быть допущена к дальнейшему рассмотрению. |
| BR-03 | **Согласие на обработку персональных данных** ТОЛЬКО ЕСЛИ получено согласие на обработку перс данных заявка может быть создана. |
| BR-04 | **Одна открытая заявка** У одного клиента может быть только одна открытая заявка. |
| BR-05 | **Недоступность СПР** В случае недоступности СПР выполнять ретраи каждые 5 мин в течении часа, далее перевести заявку на оператора |


## 2.2 Функциональные требования: 

- При получении от клиента данных, необходимых для оформления микрозайма, система должна создать заявку на получение микрозайма

- До отправки формы на оформление займа система должна получить и зафиксировать согласие клиента на обработку персональных данных

- При успешном создании заявки система должна проверить соответствие клиента установленным требованиям к возрасту и гражданству

- После успешного прохождения проверки требований к возрасту и гражданству система должна получить кредитную историю клиента из БКИ, система успешно получает предусмотренный набор данных либо фиксирует предусмотренный сценарий невозможности их получения.

- При получении всех данных, необходимых для принятия решения по заявке, система должна передать данные заявки и результаты выполненных проверок в СПР, в результате СПР получает полный набор данных для принятия решения по заявке.

- При получении ответа от СПР система должна обработать результат решения по заявке, заявка получает результат автоматического решения и может перейти к оформлению займа или завершению процесса отказом.



## 2.3 Нефункциональные требования: 

1. Система должна сохранять работоспособность функции создания заявки при целевой одновременной нагрузке, значение которой необходимо определить у владельца системы. Допустимое время выполнения операции при такой нагрузке необходимо определить.

2. Сценарий получения и фиксации согласия клиента на обработку персональных данных должен успешно выполняться на всех поддерживаемых версиях iOS и Android; перечень версий остается открытым вопросом.

3. Система должна обеспечивать регистрацию факта отправки запроса в БКИ и связанных с ним событий обработки таким образом, чтобы по записи можно было установить факт и время запроса, идентификатор заявки и результат взаимодействия. Состав и срок хранения логов необходимо определить. (Аудируемость)

4. Система должна обработать полученный от СПР результат рассмотрения заявки в установленное время. Допустимое максимальное время обработки ответа необходимо определить с бизнес-заказчиком.

# 3. User Story

## US-01. Подача заявки на онлайн-микрозайм

Как потенциальный заёмщик, я хочу подать заявку на получение микрозайма онлайн, чтобы получить возможность оформить заём быстро и без посещения отделения банка.

### Acceptance Criteria

**AC-01. Успешная подача заявки**

- **Дано:** потенциальный заёмщик заполнил все обязательные поля формы и предоставил согласие на обработку персональных данных.
- **Когда:** заёмщик отправляет заявку на микрозайм.
- **Тогда:** система создаёт заявку, присваивает ей уникальный идентификатор и позволяет продолжить процесс оформления.

**AC-02. Попытка подачи заявки без согласия**

- **Дано:** потенциальный заёмщик заполнил форму, но не предоставил согласие на обработку персональных данных.
- **Когда:** заёмщик пытается отправить заявку.
- **Тогда:** система не отправляет форму на оформление займа и информирует клиента о необходимости предоставить согласие.

**AC-03. Отправка заявки с незаполненными обязательными полями**

- **Дано:** потенциальный заёмщик не заполнил одно или несколько обязательных полей.
- **Когда:** заёмщик пытается отправить заявку.
- **Тогда:** система не создаёт заявку и указывает на поля, которые необходимо заполнить.


## US-02. Получение предварительного графика платежей

Как потенциальный заёмщик, я хочу получить предварительный график платежей исходя из выбранных условий микрозайма, чтобы оценить будущую финансовую нагрузку

### Acceptance Criteria

**AC-01. Формирование предварительного графика платежей**

- **Дано:** потенциальный заёмщик выбрал условия микрозайма, необходимые для расчёта графика.
- **Когда:** заёмщик запрашивает предварительный график платежей.
- **Тогда:** система формирует и отображает график платежей, соответствующий выбранным условиям микрозайма.

**AC-02. Изменение условий микрозайма**

- **Дано:** потенциальный заёмщик получил предварительный график платежей.
- **Когда:** заёмщик изменяет одно или несколько условий микрозайма, влияющих на график.
- **Тогда:** система пересчитывает и отображает предварительный график с учётом изменённых условий.

**AC-03. Недостаточно данных для расчёта**

- **Дано:** потенциальный заёмщик не указал все условия, необходимые для расчёта графика.
- **Когда:** заёмщик запрашивает предварительный график платежей.
- **Тогда:** система сообщает, какие данные необходимо указать для расчёта графика.

## US-03. Предоставление согласия на обработку персональных данных

Как потенциальный заёмщик, я хочу понимать, какие именно персональные данные будут использованы для скоринга, чтобы осознанно принять решение о предоставлении согласия на их обработку.

### Связи между сущностями ER-диаграммы

- `CLIENT ||--o{ CLAIM` — один клиент может подать много заявок. Каждая заявка принадлежит одному клиенту. **Связь 1:N**.

- `PRODUCT ||--o{ CLAIM` — один кредитный продукт может быть выбран во многих заявках. Каждая заявка связана с одним продуктом. **Связь 1:N**.

- `CLAIM }o--|| STATUS` — много заявок могут иметь один статус. У каждой заявки ровно один текущий статус. **Связь N:1**.

- `CLAIM ||--o{ CLAIM_REASON` — одна заявка может иметь несколько причин. Каждая запись в CLAIM_REASON относится к одной заявке. **Связь 1:N**.

- `REASON ||--o{ CLAIM_REASON` — одна причина может встречаться в нескольких заявках. Каждая запись в CLAIM_REASON ссылается на одну причину. **Связь 1:N**.

**Примечание:** Сущность `CLAIM_REASON` реализует связь многие ко многим (M:N) между `CLAIM` и `REASON`.


# 8. Проектирование API

## 8.1. Общая схема API

**Назначение API:** обеспечить создание заявок на микрозайм, получение информации о конкретной заявке и просмотр списка заявок бизнес-пользователями.

| № | Операция | HTTP method | Path | Назначение | Инициатор |
|---|---|---|---|---|---|
| 1 | Create claim | `POST` | `/v1/claims` | Создание заявки на микрозайм | Мобильное приложение |
| 2 | Get claim | `GET` | `/v1/claims/{claimId}` | Получение деталей и текущего статуса заявки | Мобильное приложение |


В API используется ресурс `claims`, представляющий заявки на микрозайм.

Кредитный конвейер управляет обработкой заявки, взаимодействует с внешними системами GCP, БКИ и СПР, получает результаты проверок и обновляет статус заявки. Взаимодействия с внешними системами являются внутренними процессами и не входят в перечень трёх рассматриваемых публичных API-операций.

---

## 8.2. Операция № 1 — Create claim

### Назначение

Создание заявки на микрозайм после выбора клиентом условий займа и получения согласия на обработку персональных данных.

- **HTTP method:** `POST`
- **Path:** `/v1/claims`
- **Path-параметры:** отсутствуют.
- **Query-параметры:** отсутствуют.
- **Request body:** JSON.
- **Успешный HTTP status:** `200 OK`.

### Request body

```json
{
"loan": {
    "productId": 10,
    "requestedAmount": 5000000,
    "termDays": 12
  },
  "client": {
    "bank_client_id": "787878",
    "phone": "+998901234567",
    },
"consent": {
"consentReceived": true,
"consentData": "2026-05-15"
}}
```

### Успешный response

```json
{
  "claimId": 741  
}
```

**Описание полей Request:**

| Название поля | Обязательность | Тип данных | Описание |
|---|---|---|---|
| `client` | Да | Object | Объект с данными клиента |
| `client.bank_client_id` | Да | String | Уникальный идентификатор клиента в банковской системе, полученный мобильным приложением из токена авторизации |
| `client.phone` | Да | String | Номер телефона клиента в международном формате |
| `loan` | Да | Object | Объект с параметрами займа |
| `loan.productId` | Да | Integer | Идентификатор кредитного продукта; положительное целое число |
| `loan.requestedAmount` | Да | Integer | Запрашиваемая сумма займа; положительное целое число, соответствующее ограничениям продукта |
| `loan.termDays` | Да | Integer | Срок займа в днях; положительное целое число, соответствующее условиям продукта |
| `consent` | Да | Object | Объект с информацией о согласии на обработку персональных данных |
| `consent.consentReceived` | Да | Boolean | Признак подтверждения согласия. Для создания заявки значение должно быть `true` |
| `consent.consentData` | Да | String | Дата получения согласия в формате `YYYY-MM-DD` |

**Описание полей Response:**

- Создание заявки выполняется только при наличии действительного согласия клиента consent.consentData = SYSDATE

## 8.3. Операция № 2 — Get claim

### Назначение

Получение деталей конкретной заявки и её текущего статуса для отслеживания процесса рассмотрения клиентом.

- **HTTP method:** `GET`
- **Path:** `/v1/claims/{claimId}`
- **Path-параметры:** `claimId` — идентификатор заявки.
- **Query-параметры:** отсутствуют.
- **Request body:** отсутствует.
- **Успешный HTTP status:** `200 OK`.

### Пример запроса

```http
GET /v1/claims/741
```

### Успешный response

```json
{
  "claimId": 741,
  "status": "under_review",
  "requestedAmount": 5000000,
  "termMonth": 12,
  "createdAt": "2026-10-11T10:30:00Z",
  "updatedAt": "2026-10-11T10:35:00Z",
  "decision": null,
  "rejectionReason": null
}
```

| Поле | Тип | Описание |
|---|---|---|
| `claimId` | integer | Идентификатор заявки |
| `status` | string {enum} | Текущий статус заявки |
| `requestedAmount` | integer | Запрашиваемая сумма |
| `termDays` | integer | Срок займа в месяцах |
| `createdAt` | string, date-time | Дата и время создания заявки |
| `updatedAt` | string, date-time | Дата и время последнего изменения |
| `decision` | string или null | Результат рассмотрения заявки, если определён |
| `rejectionReason` | string или null | Причина отказа, если применимо и разрешено для отображения |

Предполагаемые значения `status` enum: `created`, `under_review`, `approved`, `rejected`, `additional_review`.

### Основные ошибочные ответы

| HTTP status | Код ошибки | Описание |
|---|---|---|
| `400 Bad Request` | `INVALID_CLAIM_ID` | Идентификатор заявки имеет неверный формат |
| `401 Unauthorized` | `UNAUTHORIZED` | Пользователь не авторизован |
| `403 Forbidden` | `FORBIDDEN` | Пользователь не имеет права просматривать эту заявку |
| `404 Not Found` | `CLAIM_NOT_FOUND` | Заявка не найдена |
| `500 Internal Server Error` | `INTERNAL_ERROR` | Внутренняя ошибка сервера |

### Правила обработки

- Клиент может просматривать только собственные заявки.
- Сервер проверяет права доступа к заявке.
- Клиент получает актуальный статус, сохранённый в системе.
- Причина отказа возвращается только в объёме, разрешённом бизнес-правилами и требованиями безопасности.
