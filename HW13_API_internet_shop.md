## 1. Разбор API-контракта

**Базовый URL:** `https://api.shop.example/v1`

### 1. Получение информации о конкретном товаре

* **Назначение:** получение информации о товаре по его идентификатору.
* **Method:** `GET`
* **Path:** `/products/{productId}`
* **Path-параметры:** `productId` — идентификатор товара.
* **Query-параметры:** отсутствуют.
* **Body:** отсутствует.
* **Успешный response:** объект товара с полями:

  * `id` — идентификатор товара;
  * `name` — название товара;
  * `price` — цена;
  * `status` — статус товара.

### 2. Получение списка товаров с фильтрацией

* **Назначение:** получение списка товаров, соответствующих заданным фильтрам.
* **Method:** `GET`
* **Path:** `/products`
* **Path-параметры:** отсутствуют.
* **Query-параметры:**

  * `category` — категория товара;
  * `status` — статус товара.
* **Body:** отсутствует.
* **Успешный response:** массив товаров. Каждый товар содержит:

  * `id` — идентификатор товара;
  * `name` — название товара;
  * `price` — цена;
  * `status` — статус товара.

### 3. Создание заказа

* **Назначение:** создание нового заказа на товар.
* **Method:** `POST`
* **Path:** `/orders`
* **Path-параметры:** отсутствуют.
* **Query-параметры:** отсутствуют.
* **Body:**

  * `productId` — идентификатор товара;
  * `quantity` — количество товара;
  * `customerId` — идентификатор покупателя;
  * `createdAt` — дата и время создания заказа;
  * `finalAmount` — итоговая сумма заказа.
* **Успешный response:**

  * `orderId` — идентификатор созданного заказа;
  * `status` — статус заказа;
  * `amount` — сумма заказа.

### 4. Изменение статуса заказа

* **Назначение:** изменение статуса существующего заказа.
* **Method:** `PUT`
* **Path:** `/orders`
* **Path-параметры:** отсутствуют.
* **Query-параметры:** отсутствуют.
* **Body:**

  * `orderId` — идентификатор заказа;
  * `status` — новый статус заказа.
* **Успешный response:**

  * `orderId` — идентификатор заказа;
  * `status` — новый статус заказа.

### 5. Получение информации о заказе

* **Назначение:** получение информации о конкретном заказе по его идентификатору.
* **Method:** `GET`
* **Path:** `/orders/{orderId}`
* **Path-параметры:** `orderId` — идентификатор заказа.
* **Query-параметры:** отсутствуют.
* **Body:** отсутствует.
* **Успешный response:**

  * `orderId` — идентификатор заказа;
  * `customerId` — идентификатор покупателя;
  * `status` — статус заказа;
  * `amount` — сумма заказа.

## 2. Решения контракта, которые стоит обсудить при API Review

### 1. `PUT /orders`, а `orderId` передаётся в body

* **Что вызывает вопрос:** идентификатор заказа находится в `body`, хотя для получения заказа используется `GET /orders/{orderId}`.
* **Почему это может быть проблемой:** по URL непонятно, какой именно заказ изменяется. Контракт получается непоследовательным.
* **Как можно изменить:** использовать `PUT /orders/{orderId}` и передавать в body только изменяемые данные.

### 2. Использование `PUT` для изменения только статуса

* **Что вызывает вопрос:** при выполнении `PUT` изменяется только поле `status`.
* **Почему это может быть проблемой:** `PUT` обычно используется для полной замены ресурса, а здесь фактически выполняется частичное изменение заказа.
* **Как можно изменить:** рассмотреть использование `PATCH /orders/{orderId}`.

### 3. `createdAt` передаётся клиентом

* **Что вызывает вопрос:** дата и время создания заказа (`createdAt`) передаются в request body.
* **Почему это может быть проблемой:** клиент может передать некорректную дату или время. Возникает вопрос, кто является источником истины для времени создания заказа.
* **Как можно изменить:** убрать `createdAt` из request и формировать дату и время создания заказа на стороне сервера.

### 4. `finalAmount` передаётся клиентом

* **Что вызывает вопрос:** итоговая сумма заказа (`finalAmount`) определяется и передаётся consumer.
* **Почему это может быть проблемой:** клиент может передать сумму, которая не соответствует цене товара, количеству, скидкам или другим бизнес-правилам.
* **Как можно изменить:** рассчитывать итоговую сумму на стороне сервера на основании данных заказа.

### 5. `status` представлен обычной строкой

* **Что вызывает вопрос:** поле `status` имеет тип string, но список допустимых значений и правила их изменения не определены.
* **Почему это может быть проблемой:** разные consumer могут использовать разные значения или написание статуса. Также непонятно, какие переходы между статусами разрешены.
* **Как можно изменить:** определить перечень допустимых статусов и правила перехода между ними, например `created → paid → processing → shipped → delivered`.

### 6. Неясное различие между `price`, `amount` и `finalAmount`

* **Что вызывает вопрос:** в разных операциях используются три похожих поля: `price`, `amount` и `finalAmount`.
* **Почему это может быть проблемой:** из контракта неясно, что именно означает каждое поле: цена одной единицы товара, сумма заказа или итоговая сумма после скидок.
* **Как можно изменить:** явно определить назначение полей и при необходимости переименовать их, например использовать `unitPrice` и `totalAmount`.

### 7. Не указана валюта

* **Что вызывает вопрос:** цена и сумма представлены только числом, например `15990`.
* **Почему это может быть проблемой:** невозможно определить валюту. При расширении магазина на другие страны это может привести к неоднозначности.
* **Как можно изменить:** добавить поле `currency`, например `"currency": "UZS"`.

### 8. `customerId` передаётся клиентом

* **Что вызывает вопрос:** при создании заказа consumer самостоятельно передаёт `customerId`.
* **Почему это может быть проблемой:** если пользователь авторизован, клиент потенциально может указать идентификатор другого покупателя.
* **Как можно изменить:** определять `customerId` на стороне сервера из данных авторизации, а не принимать его из request body.


## 3. Отдельный разбор `POST /orders`

### Должен ли consumer передавать `createdAt`?

Скорее **нет**.

`createdAt` — это дата и время фактического создания заказа. Это системное значение, которое должно формироваться на стороне сервера в момент создания заказа.

Если consumer передаёт это поле самостоятельно, он может отправить некорректное значение: например, дату в прошлом, будущем или время из своей локальной системы.

Поэтому лучше, чтобы consumer не передавал `createdAt`.

### Должен ли consumer передавать `finalAmount`?

Также **нет**.

Итоговая сумма заказа должна рассчитываться сервером на основании данных заказа и бизнес-правил.

Например, итоговая сумма может зависеть от:

* цены товара на момент оформления;
* количества товара;
* скидки;
* промокода;
* стоимости доставки;
* налогов;
* других правил магазина.

Если consumer сам передаёт `finalAmount`, серверу приходится решать, доверять ли этой сумме или пересчитывать её.

### Кто должен быть источником истины?

Для обоих значений источником истины должен быть **сервер**:

* `createdAt` — сервер определяет по фактическому времени создания заказа;
* `finalAmount` — сервер рассчитывает на основании актуальных данных и бизнес-правил.

Consumer должен передавать только те данные, которые действительно необходимы для создания заказа.

### Пример безопасного request?


```json
{
  "productId": 125,
  "quantity": 1,
  "customerId": 456
}
```

После обработки сервер сам определяет:

```text
createdAt → текущее время сервера
finalAmount → рассчитывается сервером
```

А в response можно вернуть уже рассчитанные значения:

```json
{
  "orderId": 741,
  "status": "created",
  "amount": 15990,
  "createdAt": "2026-09-12T15:30:00Z"
}
```

Таким образом, consumer предоставляет входные данные для создания заказа, а сервер отвечает за системные значения и расчёт итоговой суммы.

## 4. Отдельный разбор `PUT /orders`

### Достаточно ли path `/orders`?

Скорее **нет**.

Операция изменяет конкретный заказ, но в URL не указан его идентификатор:

```http
PUT /orders
```

При этом `orderId` передаётся внутри body:

```json
{
  "orderId": 741,
  "status": "cancelled"
}
```

Из URL невозможно определить, какой именно заказ изменяется.

### Где логичнее передавать `orderId`?

Логичнее передавать `orderId` в **path**:

```http
PUT /orders/741
```

Потому что `741` идентифицирует конкретный ресурс — заказ.

Это также соответствует уже существующему контракту:

```http
GET /orders/{orderId}
```

То есть получение и изменение одного и того же ресурса будут использовать одинаковый способ идентификации.

### Соответствует ли `PUT` смыслу операции?

Здесь есть спорный момент.

В исходном контракте меняется только одно поле:

```json
{
  "status": "cancelled"
}
```

То есть весь заказ не заменяется — изменяется только его статус.

Поэтому для такой операции более естественным вариантом может быть `PATCH`, который предназначен для частичного изменения ресурса.

### Можно ли использовать другой вариант контракта?

Да.

Например:

```http
PATCH /orders/{orderId}
```

Request:

```json
{
  "status": "cancelled"
}
```

Здесь:

* `orderId` идентифицирует заказ через path;
* `status` содержит изменение;
* `PATCH` показывает, что изменяется только часть ресурса.

### Улучшенный вариант

Я бы предложила следующий контракт:

```http
PATCH /orders/{orderId}
```

Request:

```json
{
  "status": "cancelled"
}
```

Response:

```json
{
  "orderId": 741,
  "status": "cancelled"
}
```

Такой вариант делает контракт более однозначным: URL определяет, **какой заказ** изменяется, а body — **что именно в нём изменяется**.

## 5. Разбор `GET /products?category=coffee&status=available`

### Почему `category` и `status` являются query parameters?

Потому что они используются для **фильтрации коллекции товаров**, а не для идентификации конкретного товара.

Запрос:

```http
GET /products?category=coffee&status=available
```

можно прочитать как:

> «Дай мне коллекцию товаров `/products`, но оставь только товары категории `coffee` со статусом `available`.»

`category` и `status` не определяют один конкретный ресурс — они задают условия поиска внутри коллекции.

### Чем этот запрос отличается от `GET /products/{productId}`?

`GET /products/{productId}` используется для получения **конкретного товара**, идентифицированного по ID.

Например:

```http
GET /products/125
```

Здесь `125` — уникальный идентификатор ресурса.

В ответ ожидается один конкретный товар:

```json
{
  "id": 125,
  "name": "Coffee machine",
  "price": 15990,
  "status": "available"
}
```

А:

```http
GET /products?category=coffee&status=available
```

используется для получения **коллекции товаров**, подходящих под заданные условия.

В ответе может быть:

```json
[
  {
    "id": 125,
    "name": "Coffee machine",
    "price": 15990,
    "status": "available"
  }
]
```

или несколько товаров.

### Что изменится в смысле запроса?

Если использовать /products/coffee, меняется смысл операции: coffee становится частью идентификации ресурса в path, а не условием фильтрации коллекции. 
Такой вариант может быть оправдан, если категория рассматривается как отдельный ресурс, например /categories/coffee, но для фильтрации товаров предпочтительнее GET /products?category=coffee.

## 6. Определение совместимости изменений

Исходный response:

```json
{
  "id": 125,
  "name": "Coffee machine",
  "price": 15990,
  "status": "available"
}
```

### а) Добавлено необязательное поле `currency`

```json
"currency": "RUB"
```

* **Совместимость:** совместимое изменение.
* **Почему:** существующие consumer могут продолжать работать с прежними полями. Новое поле является необязательным и не требует от consumer его обработки.
* **Новая major-версия:** не требуется.

**Риск:** низкий. Однако плохо написанный consumer, который строго проверяет структуру response и запрещает неизвестные поля, теоретически может потребовать доработки.

---

### б) Поле `name` переименовано в `productName`

* **Совместимость:** breaking change.
* **Почему:** consumer, который обращается к полю `name`, больше не сможет получить его значение. Фактически существующее поле удаляется, а вместо него появляется другое.
* **Новая major-версия:** требуется.

---

### в) `id` изменён с `integer` на `string`

* **Совместимость:** breaking change.
* **Почему:** изменяется тип существующего поля. Consumer может ожидать число и выполнять с ним числовые операции, сравнение или десериализацию в `integer`.
* **Новая major-версия:** требуется.

Например, было:

```json
"id": 125
```

а станет:

```json
"id": "125"
```

Для consumer это уже другой тип данных.

---

### г) Добавлен новый endpoint

```http
GET /products/{productId}/reviews
```

* **Совместимость:** совместимое изменение.
* **Почему:** существующие endpoint и response не изменяются. Новый endpoint добавляет новую возможность, но не влияет на существующих consumer.
* **Новая major-версия:** не требуется.

---

### д) Добавлен необязательный query parameter `language`

Например:

```http
GET /products?language=ru
```

* **Совместимость:** совместимое изменение, если параметр действительно необязательный и при его отсутствии поведение API сохраняется.
* **Почему:** существующие запросы продолжают работать без нового параметра.
* **Новая major-версия:** не требуется.

---

### е) `price` раньше означал рубли, а теперь копейки

* **Совместимость:** breaking change.
* **Почему:** формально тип поля не изменился — это по-прежнему число. Но **изменился смысл и единица измерения данных**.

Например, раньше:

```json
"price": 15990
```

означало `15 990 рублей`.

После изменения:

```json
"price": 1599000
```

означает `15 990 рублей`, но уже в копейках.

Существующий consumer может продолжить технически успешно получать поле `price`, но интерпретировать значение неправильно. Это особенно опасный тип breaking change, потому что ошибка может быть незаметной на уровне API-контракта.

* **Новая major-версия:** требуется.

---

### ж) Из enum `status` удалено значение `available`

* **Совместимость:** breaking change.
* **Почему:** существующий consumer может получать `available` и ожидать это значение. После его удаления consumer перестанет корректно обрабатывать такой статус.
* **Новая major-версия:** требуется.

---

### з) В enum `status` добавлено новое значение `reserved`

* **Формальная совместимость:** потенциально совместимое изменение.
* **Новая major-версия:** формально не требуется.

Но здесь есть **риск для существующего consumer**.

Если consumer реализован правильно и умеет обрабатывать неизвестные значения enum, проблем может не возникнуть.

Однако если consumer ожидает строго:

```text
created
available
cancelled
```

и не умеет обрабатывать `reserved`, новый статус может привести к ошибке.

Например, consumer может содержать логику:

```text
если status = available → показать товар
если status = cancelled → скрыть товар
иначе → ошибка
```

Поэтому добавление нового значения в enum может быть **формально совместимым, но потенциально breaking на практике**.

### Итоговая классификация

| Изменение                                | Совместимость                      | Major                                    |
| ---------------------------------------- | ---------------------------------- | ---------------------------------------- |
| а) Добавление необязательного `currency` | Совместимое                        | Нет                                      |
| б) `name` → `productName`                | Breaking                           | Да                                       |
| в) `id`: integer → string                | Breaking                           | Да                                       |
| г) Новый endpoint `/reviews`             | Совместимое                        | Нет                                      |
| д) Новый необязательный `language`       | Совместимое                        | Нет                                      |
| е) `price`: рубли → копейки              | Breaking                           | Да                                       |
| ж) Удаление `available` из enum          | Breaking                           | Да                                       |
| з) Добавление `reserved` в enum          | Формально совместимое, но с риском | Обычно нет, но требует проверки consumer |

## 7. Финальный кейс по версионированию

### Исходный контракт

```http
GET /v1/orders/{orderId}
```

Response:

```json
{
  "orderId": 741,
  "status": "created",
  "amount": 15990
}
```

Команда планирует изменить контракт.

### Какие изменения можно оставить в `v1`

**1. Добавить новый endpoint поиска заказов**

Например:

```http
GET /v1/orders/search
```

или:

```http
GET /v1/orders?status=created
```

Если новый endpoint не изменяет существующие операции и не меняет существующие response, его можно добавить в `v1`.

**Почему:** добавление нового endpoint не ломает существующих consumer.

---

**2. Добавить необязательный фильтр `status`**

Например:

```http
GET /v1/orders?status=created
```

При отсутствии параметра:

```http
GET /v1/orders
```

поведение остаётся прежним.

**Почему:** существующие запросы продолжают работать без нового параметра. Поэтому изменение является обратно совместимым.

---

**3. Добавить поле `currency`**

Например:

```json
{
  "orderId": 741,
  "status": "created",
  "amount": 15990,
  "currency": "RUB"
}
```

Само по себе добавление необязательного поля является совместимым изменением.

**Но:** в данном кейсе команда одновременно хочет изменить смысл `amount` с рублей на копейки. Поэтому безопаснее не менять существующий `amount` в `v1`, а новую модель суммы реализовать уже в `v2`.

---

### Какие изменения требуют `v2`

#### 1. Переименование `orderId` → `id`

Это breaking change.

Существующие consumer могут обращаться к полю:

```text
orderId
```

После изменения они его больше не найдут.

Поэтому переименование лучше сделать в `v2`:

```json
{
  "id": 741
}
```

---

#### 2. Переименование `status` → `orderStatus`

Это также breaking change.

Consumer, использующий:

```text
status
```

перестанет получать ожидаемое поле.

Поэтому изменение следует перенести в `v2`:

```json
{
  "orderStatus": "created"
}
```

---

#### 3. Изменение `amount` с рублей на копейки

Это breaking change.

Тип поля может остаться числовым, но изменяется **семантика значения**.

В `v1`:

```json
"amount": 15990
```

означает 15 990 рублей.

В новой версии:

```json
"amount": 1599000
```

означает 15 990 рублей в копейках.

Существующий consumer может продолжить технически успешно получать поле `amount`, но неправильно интерпретировать его значение.

Поэтому это изменение требует `v2`.

---

### Итог

| Изменение                               | Оставить в v1 | Перенести в v2 | Причина                                    |
| --------------------------------------- | ------------: | -------------: | ------------------------------------------ |
| Переименовать `orderId` → `id`          |             ❌ |              ✅ | Breaking change                            |
| Переименовать `status` → `orderStatus`  |             ❌ |              ✅ | Breaking change                            |
| Изменить `amount` с рублей на копейки   |             ❌ |              ✅ | Меняется смысл значения                    |
| Добавить `currency`                     |            ✅* |              — | Новое поле само по себе совместимо         |
| Добавить новый endpoint поиска заказов  |             ✅ |              — | Не изменяет существующие операции          |
| Добавить необязательный фильтр `status` |             ✅ |              — | Старое поведение сохраняется без параметра |

* Однако в рамках этого кейса разумнее добавить `currency` вместе с новой моделью суммы в `v2`, чтобы не создавать неоднозначность в `v1`.

---

## Как может выглядеть `v1`

Существующий контракт продолжает работать без изменений:

```http
GET /v1/orders/{orderId}
```

```json
{
  "orderId": 741,
  "status": "created",
  "amount": 15990
}
```

При этом в `v1` можно добавить новые возможности:

```http
GET /v1/orders?status=created
```

и новый endpoint поиска заказов, если он действительно не изменяет существующие операции.

---

## Как может выглядеть `v2`

В новой версии можно сразу реализовать все необходимые breaking changes:

```http
GET /v2/orders/{id}
```

Response:

```json
{
  "id": 741,
  "orderStatus": "created",
  "amount": 1599000,
  "currency": "RUB"
}
```

Здесь:

* `orderId` заменён на `id`;
* `status` заменён на `orderStatus`;
* `amount` хранится в копейках;
* `currency` явно определяет валюту.

---

## План миграции клиентов с v1 на v2

### Шаг 1. Запустить `v2`

Опубликовать новую версию API, не отключая `v1`.

На этом этапе одновременно работают:

```text
/v1/orders/...
/v2/orders/...
```

### Шаг 2. Обновить документацию

Для consumer необходимо явно описать различия между версиями:

* `orderId` → `id`;
* `status` → `orderStatus`;
* `amount` теперь передаётся в копейках;
* добавлено поле `currency`.

Особенно важно предупредить об изменении единицы измерения `amount`.

### Шаг 3. Мигрировать consumer

Каждая система постепенно переводится с:

```text
v1 → v2
```

При этом consumer должен обновить свою модель данных и логику обработки суммы.

### Шаг 4. Контролировать использование v1

Можно отслеживать, какие consumer ещё используют `v1`, и связаться с ними до окончания поддержки старой версии.

**Итоговая идея:** в `v1` оставляем только обратно совместимые изменения, а изменения, которые ломают существующий контракт или меняют смысл данных, переносим в `v2`. При этом `v1` некоторое время продолжает работать параллельно с `v2`, чтобы дать consumer возможность спокойно мигрировать.
